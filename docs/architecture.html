Breeze
Breeze사전은 어떻게 움직이나파일 구조로드맵

Architecture

원칙

  1. 원본 PDF/EPUB Blob은 사용자의 기기에만 저장하고 서버 동기화 payload에 넣지 않습니다.
  2. 추출 본문, 보수적인 블록 정보, 원본 위치 지도는 서로 분리합니다.
  3. 목차 UI와 AI 전권 조판은 실행 경로에 포함하지 않습니다.
  4. 빌드 도구 없이도 기존 정적 배포 방식을 유지합니다.
  5. 파일 간 의존성은 index.html의 script 순서로 명시합니다.

    • classics.js: 내장 무료 고전 목록과 받기

    • mode-bridge.js: 문장 단위 비교. 줄바꿈·따옴표·공백·붙임글자 차이를 무시하고, 읽던 자리에 가장 가까운 자리를 고릅니다
    • original-session.js: 원본 세션 상태·수명·앵커·진행도
    • pdf-original.js / epub-original.js: 형식별 렌더링·단어 선택·앵커
    • original-formats.js: 형식별 일감 표(pdf·epub)와 bookSupportsOriginal()
    • reader-modes.js: 글자 ↔ 원본 전환과 전환 표시
    • reader.js: 글자 화면 렌더링, 스크롤·폭 변화 대응
  • scripts/ui/: 보기 설정, 발음, 시트 제스처
  • scripts/sync/: 로그인, 단어·위치·책 동기화
  • server/dict/: 사전 Edge Function. AI 를 부르는 갈래는 둘입니다 — look(낱말+문장 → 뜻·문장 설명·다른 뜻 후보, 왕복 한 번)과 explain(문장 하나 → 해석 + 왜 어려운지, 로그인 필수·하루 5번). 나머지는 warm(함수만 깨움), log(사람이 무엇을 했는지 기록), seed(맛보기 글의 답을 미리 받아 두기), delete_account(이 사람이 서버에 가진 것을 전부 지우기). 예전 entry/pick 3분할은 서버에 낱말 항목을 쌓아 두던 구조에 딸린 것이라 함께 접었습니다. 왜 그런지는 DICT.md, 표는 sql/supabase_dict.sql
  • server/article/: 기사 HTML·사진 중계 Edge Function (추출은 하지 않습니다)
  • assets/classics/: 함께 배포하는 퍼블릭 도메인 EPUB 3종과 그 표지 그림. 표지는 EPUB 안이 아니라 파일 밖의 .jpg 가 이깁니다 — 한 장 갈아 끼우면 권유 카드와 서가가 함께 바뀝니다 (README.md)
  • assets/samples/: 첫 화면에 놓이는 맛보기 기사와 사진 자리 (README.md 에 무엇을 넣으면 되는지)
  • modules/exam-shorts/: 연결 해제된 기출 문항 분리 + 쇼츠 화면. index.html이 읽지 않습니다. 되살리는 순서는 그 폴더의 README.md에 있고, exam.js의 규칙은 떼어 둔 동안에도 npm test가 계속 검사합니다.

홈

두 줄입니다. Casuals(kind: paste | article)는 가로 레일, Books(그 밖의 전부 + 아직 안 받은 내장 고전)은 격자. "이어서 읽기" 칸은 만들지 않았습니다 — 만들면 같은 책이 한 화면에 두 번 나옵니다. 대신 마지막에 열었던 것 하나에 테두리를 두르고 진행도 글귀 앞에 이어서를 붙입니다.

두 줄 모두 최근에 읽던 것이 앞입니다(byRecentlyRead()). 한 번도 열지 않은 것은 그 뒤에 넣은 순서로 놓입니다. 읽던 것을 늘 첫 칸에서 찾을 수 있으면 정렬 단추가 필요 없습니다. 대신 카드 색은 자리가 아니라 책에 붙입니다 (paletteOf(book)) — 줄이 자주 바뀌는데 색까지 따라 움직이면 같은 책을 눈으로 좇을 수 없습니다.

두 줄은 각자 자기 줄의 마지막 것을 기억합니다(nowReadingIn(list)). 지하철에서 기사를 한 편 봤다고 읽던 원서 표시가 사라지면 안 되기 때문입니다. 줄마다 라이브러리(#v-casuals · #v-longform)와 +가 하나씩 있고, 두 라이브러리는 같은 카드를 격자에만 다시 깝니다.

+가 여는 것은 그 줄에 넣을 수 있는 것뿐입니다. Casuals 는 붙여넣기·기사 URL 두 가지라 시트를 열고, Books 는 파일 하나뿐이라 시트를 건너뛰고 곧장 파일 고르기로 갑니다. 상단바의 +만 셋을 다 보여줍니다.

빈 서가로 시작하지 않습니다. 처음 여는 사람에게는 맛보기 기사 두 편이 놓이고 (samples.js), 무료 고전 세 권이 권유 카드로 뜹니다. 맛보기는 한 번만 넣습니다 — 지운 사람에게 다시 밀어 넣지 않습니다.

카드를 꾹 누르면 정보 바꾸기 시트(book-edit.js)가 열립니다. 제목과 표지를 고치고 지우는 것도 여기서 합니다. 표지는 그 기사가 데려온 사진, EPUB 안에 들어 있던 표지(epubCoverImage), 또는 그림 파일에서 고릅니다 — 두 줄의 카드가 같은 applyCover()를 씁니다.

모서리의 ✕ 는 없습니다. 오른쪽 위는 백업 화살표 자리인데, 둘이 한 모서리를 나눠 쓰다 보니 화살표가 없는 상황(로그인 전)에서 ✕ 가 빈자리를 비켜서서 혼자 어정쩡하게 떠 있었습니다. ✕ 가 남은 곳은 흐린 서버 카드 하나뿐입니다 — 거기 있는 책은 이 기기에 없어서 꾹 눌러 열 것이 없고, 그 단추가 서버 사본을 지우는 유일한 길입니다.

지우기는 두 갈래로 물어봅니다. 예전에는 한 번 누르면 서버까지 함께 지워서, 폰에서 자리만 비우려던 사람이 노트북의 책까지 잃었습니다. 되돌릴 수 없는 쪽을 기본으로 두면 안 됩니다. 이 기기에서만은 서버 사본을 그대로 두고 톰스톤도 남기지 않으므로, Sync 창에 이 기기에 받기로 다시 나타납니다.

내장 고전은 별도 읽기 경로가 없습니다. 카드를 누르면 assets/classics의 EPUB을 fetch해서 File로 만들어 평범한 importFile()에 넘깁니다. 그래서 원본 모드, 단어장, 동기화가 전부 저절로 따라옵니다.

기사 URL

본문 추출은 기기 안에서 브라우저의 DOMParser로 합니다. 규칙만 씁니다.

  1. script·style·nav·header·footer·aside·form·table·figure 따위를 먼저 지웁니다.
  2. 본문 뿌리 = 50자 넘는 <p>가 가장 많이 모인 조상. 위로 갈수록 점수를 깎아 페이지 전체가 이기지 않게 합니다. 사이트가 <article>을 붙여 두었고 그 안에 본문이 들어 있으면 그쪽을 씁니다.
  3. 클래스·id에 comment·promo·related·reference 같은 말이 있으면 버립니다. 각주처럼 자기 자신은 깨끗한 경우가 있어 조상 네 칸까지 봅니다.
  4. References·External links 같은 소제목을 만나면 거기서 멈춥니다.
  5. 끝에 붙는 Most viewed 같은 것은 언제나 짧으므로, 마지막 진짜 문단(100자 이상) 뒤를 통째로 자릅니다.
  6. 본문이 500자에 못 미치면 실패로 봅니다. 로그인·결제가 걸린 기사가 여기 걸리며, 그때는 "못 가져왔다"고 말하고 붙여넣기를 권합니다.

X(트위터) 글

X 한 장에는 <article>이 여럿입니다. 첫 번째가 그 글, 나머지는 답글입니다. 그대로 두면 답글 본문과 답글에 딸린 사진까지 책에 들어옵니다. 그래서 긴 문단이 가장 많은 <article> 하나만 남기고 나머지를 지운 뒤, 그것을 본문 뿌리로 바로 지정합니다 — querySelector('article, …, main')은 문서에 먼저 나오는 것을 주는데 X 에서는 <main>이 앞서서 화면 제목("Post")까지 딸려 왔습니다.

X 의 긴 글(Article) 은 본문 사진을 <img>로 그려 두지 않습니다. 페이지에 실려 오는 편집기 상태(DraftJS) 안에만 주소가 있고 화면은 나중에 그립니다. 그래서 DOM 만 보면 표지 한 장만 나오고 글 중간 그림이 통째로 빠집니다. 블록 목록에서 type:"atomic"인 자리를 찾아 바로 앞 문단의 글자를 열쇠로 화면의 같은 문단을 찾고 그 뒤에 끼웁니다. 남의 내부 형식이라 언젠가 바뀌므로, 자리 수와 사진 수가 정확히 같고 앵커가 화면에서 딱 하나 맞을 때만 넣습니다 — 하나라도 어긋나면 아무 일도 하지 않습니다. 엉뚱한 자리에 사진을 넣는 것보다 없는 편이 낫습니다.

제목도 X 만 다릅니다. og:title이 늘 "이름 (@아이디) on X"라 무슨 글인지 알 수 없어서, 본문 <h1>을 먼저 봅니다. 프로필 사진(profile_images/)은 본문 사진이 아니므로 거릅니다.

사진

사진은 대부분 <figure> 안에 있고 그 <figure>는 규칙 1에서 통째로 버려집니다. 그래서 버리기 전에 articleMarkImages()가 자리를 남기는 표시 하나로 바꿔 둡니다. 순서가 뒤집히면 사진이 전부 사라집니다.

  • srcset이 있으면 가장 큰 판을 씁니다. 화면에 처음 뜨는 480px 판을 그대로 담으면 카드 표지가 뭉개집니다.
  • 크기는 긴 변으로 봅니다(200px 미만이면 아이콘). 두 변을 다 재면 250×144 같은 가로 사진이 함께 걸러집니다. 짧은 변은 60px 미만만 막습니다(구분선).
  • 걸러낼 때는 그 <img> 하나만 버립니다. 담고 있는 <figure>까지 지우면 안 됩니다 — BBC는 사진과 매체 로고를 한 <figure>에 같이 넣어 두어서, 로고를 버리다 사진이 통째로 날아갔습니다.
  • 한 편에 최대 8장. 세는 것은 살아남은 것만입니다. 표시할 때 세면 표 안의 배지처럼 곧 버려질 그림이 자릿수를 차지해 본문 사진이 밀려납니다.
  • 대표 사진은 og:image, 없으면 본문 첫 사진. Casuals 카드의 표지가 됩니다.

받은 사진은 넣는 순간 IndexedDB(imgs)에 담습니다. 주소만 들고 있으면 비행기 안에서 빈 칸이 되고, 읽을 때마다 그 매체 서버에 발자국이 남습니다. 저장 키는 art|<주소 해시>입니다 — 책 ID는 그 키가 들어간 문단이 다 모여야 정해지므로, 키가 책 ID에 기댈 수 없습니다. 못 받은 사진은 조용히 빼고 문단을 다시 조립합니다. 사진 하나 때문에 기사를 통째로 못 읽으면 손해입니다.

사진과 동기화

사진은 글과 함께 갑니다(photos). 예전에는 주소만 보내고 받는 기기가 그 매체 서버에서 다시 받게 했습니다. 자주 실패합니다 — 매체는 흔히 자기 페이지에서 온 요청에만 사진을 내주고, CDN 주소는 며칠이면 바뀌며, 중계를 한 번 더 타야 합니다. 그래서 폰에서 받은 기사는 어떤 건 사진이 뜨고 어떤 건 안 떴습니다. 이미 기기에 있는 바이트를 실어 보내면 그 갈림이 사라집니다.

보내기 전에 한 번 굽습니다(shrinkPhotoForTransport). 매체가 내주는 사진은 2000~3000px 짜리 인쇄용 원본입니다. 긴 변 1400px · JPEG 로 다시 구우면 대개 6~8배 줄어듭니다 — 화면에서 달라 보이는 것은 없고, 서버에 쌓이는 양과 셀룰러로 흐르는 양만 줄어듭니다. 기기에 있는 원본은 그대로 두므로 이 기기에서 읽을 때는 늘 원본을 봅니다. 줄인 것은 보내는 판일 뿐입니다.

예산은 글 하나에 700KB(BOOK_PHOTO_BUDGET)이고, base64 로 부풀린 뒤의 길이로 셉니다 — 원본 바이트로 세면 실제로 오가는 양은 언제나 그보다 3분의 1 많습니다. 줄여서 보내므로 사진 네댓 장짜리 기사도 대개 예산 안에 들어옵니다. 표지가 먼저, 그다음 본문 차례대로 담고 예산에서 잘립니다. 잘린 사진은 지금까지처럼 imgSrc 주소로 받아 옵니다 — 없어지는 길이 아니라 뒷길입니다. 원서는 표지 한 장만 실립니다.

받아 오지 못하면(오프라인, 사이트가 사진을 내림) 그림은 조용히 빠지고 카드는 글자 표지로 돌아갑니다. 못 받은 것은 세션 동안 기억해 두어 홈을 다시 그릴 때마다 다시 부르지 않습니다.

EPUB 삽화는 이 길이 없습니다 — 받아 올 주소가 없고 사용자 파일에서 나왔기 때문입니다. 새 기기에서 원본 파일을 다시 연결하면 삽화도 함께 되살아납니다.

기사에는 연결할 원본 파일이 없습니다. 원본 모드는 PDF·EPUB 전용이고, 기사에 그에 해당하는 것은 그 사이트의 살아 있는 페이지뿐이라 오프라인으로 가져올 수 없습니다. 대신 제목 아래에 원문으로 가는 링크(#rsource)를 둡니다. 영상·인터랙티브 도표도 같은 이유로 담지 않습니다.

서버(server/article)는 CORS만 넘겨 줍니다. ?url=은 HTML을 그대로 돌려주고 파싱하지 않습니다 — 규칙을 고칠 때마다 함수를 다시 배포하고 싶지 않기 때문입니다. &as=image는 그림 바이트를 그대로 돌려줍니다. 열린 중계가 되지 않도록 사설 대역·비 HTTP 스킴을 막고 HTML은 3MB, 그림은 2MB에서 끊습니다. SVG는 그림이 아니라 스크립트를 품을 수 있는 문서라 받지 않습니다.

호환성

IndexedDB breeze-img는 버전 3으로 올라가며 originals 저장소가 추가됩니다. 기존 books와 imgs, localStorage의 진행도·단어장 키는 유지합니다.

부팅할 때마다 돌던 옛 판 변환들은 뗐습니다 — localStorage 에 있던 책 옮기기, AI 조판 결과를 formatting 으로 옮기기, readerSchema 찍기, 숫자였던 읽기 위치 바꾸기. 한 번 돌고 끝났어야 할 일이 영구 코드가 되어 있었습니다. 남긴 것은 지문 채우기 하나입니다 — 이건 변환이 아니라 서버와 짝을 맞추는 열쇠라, 어떤 경로로 들어온 책이든 있어야 합니다.

읽기 모드

  • 글자: 반복 머리말 제거, 확실한 줄 연결, EPUB 의미 태그, 강한 크기·굵기 신호만 사용합니다. 애매하면 본문입니다.
  • 2단 조판 PDF는 줄을 만들기 전에 단을 먼저 가릅니다. 글자가 거의 지나가지 않는 세로 띠를 찾는 순수 좌표 계산이며, 단이 없는 문서에서는 아무 일도 하지 않습니다. 단 경계는 쪽 경계와 같은 규칙으로 문단이 끊깁니다.
  • 형식별 일감은 ORIGINAL_FORMATS 표 하나에 모읍니다(original-formats.js). 부르는 자리마다 kind==='pdf' ? … : … 를 적던 것이 스물네 군데였습니다. 세 번째 형식은 표에 한 줄과 그 형식의 파일만 있으면 됩니다.
  • 원본 PDF: 페이지 placeholder를 먼저 만들고 현재 화면 앞뒤 페이지만 캔버스로 지연 렌더링합니다. 글자 좌표는 페이지 너비·높이 비율로 저장합니다.
  • 원본 PDF 확대는 쪽마다 제 가로 스크롤 칸 안에서 일어납니다(.pdf-page-lane). 손가락으로 화면을 벌리면 fixed 로 붙여 둔 바텀시트까지 함께 커져서, 작은 글씨를 보려고 벌릴수록 뜻이 뜨는 칸이 화면을 덮었습니다. 그래서 쪽만 키우는 ＋/− 를 둡니다. 문서 폭은 절대 늘리지 않습니다 — 처음에는 쪽을 넓히고 화면을 옆으로 스크롤하게 두었는데, 폰 브라우저는 내용이 화면보다 넓어지면 스크롤바를 주는 대신 화면 전체를 축소해 맞춰 버립니다(375px 화면이 623px 로 늘어났습니다). 확대한 만큼 그대로 되돌아가 이득이 정확히 0이었습니다. 늘린 캔버스는 흐려지므로 화면에 있는 쪽만 새 너비로 다시 그리고, 옆으로 민 비율은 하나만 들고 다니며 새로 뜨는 쪽에 얹습니다(applyPdfPan).
  • 원본 EPUB: ZIP 자원을 로컬 Blob URL로 바꾸고, 스크립트·폼·프레임을 제거한 장을 sandbox iframe에 렌더링합니다.
  • sourceMap: 문단마다 {page,y} 또는 {href,spine,element}를 저장합니다. page는 걸러낸 페이지를 뺀 순번이 아니라 실제 PDF 페이지 번호입니다. 전환할 때 가장 가까운 위치를 찾아 이동합니다.
  • 진행도는 화면의 픽셀 비율이 아니라 PDF 페이지·EPUB 장/요소·글자 문단의 논리적 위치로 계산합니다. 전환 과정에서 앱이 만든 스크롤은 저장하지 않고, 사용자 스크롤만 약 800ms 단위로 기록합니다.
  • 다만 마지막 한 화면은 예외입니다. 논리적 위치는 화면 맨 위에 무엇이 있는지로 세는데, 글 아래 여백이 화면 절반뿐이라 끝까지 내려도 마지막 조각이 맨 위까지 올라오지 못합니다. 그대로 두면 다 읽어도 100%가 되지 않습니다(문단으로 세는 기사에서 특히 두드러져 94%에서 멈췄습니다). 남은 스크롤이 한 화면 아래로 줄면 그만큼 값을 1 쪽으로 당겨, 바닥에 닿으면 정확히 1이 됩니다 — readerProgressAtEnd().
  • 전환은 sourceMap보다 눈에 보이는 문장을 먼저 씁니다. 화면 맨 위 문장을 반대쪽 화면에서 찾아 그 자리로 이동하고, 못 찾을 때만 sourceMap 좌표로 갑니다.
  • 문장 하나로는 자리를 가릴 수 없습니다. bridgeFindSequence()는 맞는 자리를 모두 모은 뒤 ① 바로 뒤 문장까지 이어서 맞는 곳 ② 더 길게 맞는 곳 ③ 읽던 자리에 가까운 곳 순으로 고릅니다. 읽던 자리를 아는데도 저 멀리(1,500낱말 밖)에서만 맞으면 그것은 우연이므로 실패로 두고 sourceMap 좌표로 돌아갑니다.

이름 없는 붙임글자

Type 3 글꼴로 조판한 PDF는 Th·ft 같은 붙임글자를 글꼴 안의 사용자 지정 자리(U+E000–U+F8FF)에 넣어 두고 그 자리가 무슨 글자인지 어디에도 적어 두지 않습니다. Type 3 는 글자마다 그림 명령일 뿐이라 글꼴 파일에 이름표도 없습니다. 그대로 두면 "The scythe"가 "□e scythe"로 보입니다.

답은 책 안에 있습니다. 같은 책에서 멀쩡히 읽힌 낱말과 맞춰 보면 후보가 하나로 좁혀집니다 — a□ernoon·so□·o□en·A□er·le□ 에 ft 를 넣으면 모두 이 책에 있는 낱말이 되고, 다른 후보는 하나도 되지 않습니다. 사전도 AI도 인터넷도 쓰지 않습니다. 1등이 2등과 비기면 손대지 않습니다 — 잘못 고친 글자는 네모보다 나쁩니다.

대소문자는 조판 규칙으로 정합니다: 문장을 여는 자리면 The, 다음 글자가 대문자면 THE, 그 밖에는 the.

정한 표는 book.glyphs에 남겨 원본 화면과 동기화가 같은 표를 씁니다. 두 화면이 붙임글자를 다르게 읽으면 같은 문장을 못 알아봅니다. 예전에 넣어 둔 책은 열 때 한 번 고칩니다.

PDF 단어 상자

PDF에는 단어가 없고 위치가 찍힌 글자 조각만 있습니다. 조각을 한 줄로 주는 책도 있지만, 글자 하나씩 주는 책도 많습니다(Verity가 그렇습니다).

"t" x=72   "h" x=76   "e" x=83.2   " " x=89.6   "t" x=93.4 …

조각마다 따로 단어를 뽑으면 글자 하나하나가 단어가 되어, 저장한 h가 페이지의 모든 h에 밑줄을 긋고 눌러도 낱글자만 찾습니다. 그래서 같은 기준선의 조각을 한 줄로 되붙인 뒤에만 단어를 나눕니다. 띄어쓰기는 조각 사이의 가로 간격으로 판단합니다(반입기의 줄 복원과 같은 규칙). 공백 조각이 알려주는 폭은 실제 간격과 다를 수 있어 쓰지 않습니다.

단어 상자는 페이지 크기 대비 비율로 저장하므로, 사전 패널이 열려 페이지 폭이 바뀌어도 다시 계산하지 않습니다. 클릭 판정과 하이라이트가 같은 상자를 씁니다. EPUB은 사용자가 더블클릭하거나 드래그한 네이티브 선택 범위를 읽습니다. 두 방식 모두 원본 글자층을 변형하지 않습니다.

보던 자리 지키기

폭이 바뀌면 글자 화면은 글이 다시 흐르고 원본 페이지는 비율대로 높이가 줄어듭니다. #readmain의 ResizeObserver가 사전 패널 개폐·창 크기 변경을 받아 방금 보던 앵커로 되돌립니다. 되돌리는 동안에는 앱이 만든 스크롤을 새 위치로 착각하지 않도록 앵커 기록을 잠급니다(holdReaderAnchor). 지연 렌더링된 PDF 페이지가 뒤늦게 실제 비율을 알게 되어 높이가 바뀔 때도, 그 페이지가 화면 위쪽에 있으면 같은 양만큼 스크롤을 옮겨 보이는 줄을 고정합니다.

로컬 원본 수명

앱은 가능한 경우 영구 저장 권한을 요청하지만 브라우저 정책이나 사용자가 사이트 데이터를 지우면 원본 Blob이 사라질 수 있습니다. 추출 본문과 서버 진행도가 남아 있으면 원본 모드에서 같은 파일을 다시 연결해 복구합니다.

서버 tombstone은 그보다 나중에 다시 반입한 로컬 원본을 지우지 않으며, 현재 열어 읽는 책에는 즉시 적용하지 않습니다. 예전 ID로 남은 원본은 파일 해시로 찾아 현재 책 ID에 다시 연결합니다.

무엇이 저절로 오가는가

짧은 글(Casuals)은 양쪽으로 저절로 움직입니다 — 넣는 즉시 올라가고 (autoUploadCasual), 다른 기기의 것은 저절로 내려옵니다 (autoDownloadCasuals). 몇 KB이고, "폰에서 담고 노트북에서 읽는다"가 이 줄이 있는 이유입니다. Sync 창을 열어 책마다 눌러야 한다면 그 일은 일어나지 않습니다.

올리는 쪽에는 따라잡기 한 번이 더 있습니다(autoUploadCasuals). 넣는 순간에만 부르면, 로그인하기 전에 담아 둔 글과 그때 인터넷이 없어서 실패한 글은 영영 올라가지 않은 채로 올라간 것처럼 보입니다. 목록을 새로 고칠 때마다 "여기 있는데 서버에 없는 짧은 글"을 마저 올립니다. 맛보기 글은 뺍니다 — 어느 기기에서든 처음 열면 저절로 생기는 것이라 서버를 거칠 이유가 없습니다.

짧은 글인지는 서버 목록의 meta.kind 로 가립니다 — 본문을 받아 봐야 알면 받을지 말지를 정할 수가 없으니까요. 그리고 kind 는 짐작이 아니라 어떻게 들어왔는지 그 자체입니다: 붙여넣기는 paste, 주소는 article, 파일은 pdf·epub·txt. 넣는 순간 적히므로 틀릴 수가 없습니다.

문제는 그 칸을 적기 전에 올라간 옛 줄뿐입니다. 두 단으로 처리합니다.

  1. 아는 기기가 대신 적어 줍니다(backfillServerKinds). 그 책을 손에 들고 있는 기기라면 짐작할 것이 없습니다 — 목록을 새로 고칠 때마다 kind 없는 줄에 알고 있는 값을 채워 넣습니다. 거의 다 여기서 끝나고, 한 번 적히면 그걸로 끝입니다.
  2. 그래도 남는 줄 — 어느 기기에도 없는, 순전히 서버에만 있는 옛 줄 — 에서만 어림짐작합니다(rowLooksCasual). 크기 하나로는 긴 기사가 원서로 넘어갈 수 있어서 문단 수를 함께 봅니다: 300KB 이하 그리고 400문단 이하. 기사는 아무리 길어도 수백 문단이고 원서는 수천 문단입니다.

이 길이 없던 동안, 옛 기사들은 Books 선반에 흐린 카드로 앉아 손으로 받히기를 기다렸습니다.

긴 글은 그대로 수동입니다. 수백 KB이고 서버가 금방 찹니다. 어차피 새 기기에서 원본 모드를 쓰려면 파일을 다시 연결해야 합니다.

이 기기에서만 지우기는 서버 사본을 남기므로, 지운 사실을 breeze.hidden에 적어 둡니다. 안 그러면 다음 동기화가 곧바로 도로 받아 와서 지운 사람 눈에는 안 지워진 것과 같습니다. Sync 창에서 손수 받으면 풀립니다.

단어·읽던 위치·책 이름은 예전처럼 주기적으로 함께 맞춥니다.

계정 — 나가는 문 두 개

로그아웃은 이 기기에서만입니다(signOut({scope:'local'})). Supabase 의 기본값은 global 이라, 그대로 두면 노트북에서 로그아웃한 사람이 폰의 갱신 토큰까지 함께 없앱니다. 폰을 든 사람은 자기가 한 적 없는 로그아웃을 당하고, 왜 그런지 알 방법도 없습니다.

계정 지우기(sbDeleteAccount → op:"delete_account")는 서버 사본을 전부 지웁니다 — Storage 의 책 파일, words·positions·books·dict_events·ai_usage, 그리고 마지막에 auth 사용자. 순서가 전부입니다: 계정을 먼저 지우면 남은 줄들이 주인을 잃고, 주인이 없으면 두 번 다시 찾아가 지울 수 없습니다. 중간에 끊기면 다시 눌러 이어서 지웁니다.

이 기기의 책과 단어장은 그대로 둡니다. "계정을 지운다"와 "읽던 것을 잃는다"는 같은 말이 아니고, 착각하면 되돌릴 수 없는 쪽으로 착각합니다.

로그인이 있는 앱은 앱 안에 이 문이 있어야 심사를 통과합니다(App Store 심사 지침 5.1.1(v)). 심사와 별개로, 나갈 문이 없는 곳에 자기 단어장을 맡기라고 할 수는 없습니다.

문장 통째로

낱말을 다 알아도 문장이 안 읽히는 때가 있습니다 — 관계절이 겹쳤거나, 도치됐거나, 낱말은 쉬운데 합쳐 놓으니 다른 뜻이 되는 관용구일 때. 그때 필요한 것은 뜻 하나가 아니라 "이 문장은 이렇게 읽는다" 입니다.

손짓은 꾹 누르기입니다. 읽는 중에는 손이 하나뿐이고 한 번 누르기는 이미 낱말이 가져갔습니다. 누르고 있는 동안 파란색이 문장에 퍼지는 것 자체가 "지금 문장을 고르고 있다"는 설명이라, 글씨로 안내할 것이 없습니다. 되돌릴 수 있어야 하므로 ① 손가락이 SENT_MOVE_SLOP(10px) 넘게 움직이면 즉시 끝, ② 다 차기 전에 떼면 아무 일도 없음. 스크롤하다 손가락이 잠깐 멈춘 것이 하루 다섯 번 중 하나를 태우면 안 됩니다.

파란색은 글자를 건드리지 않습니다. 문장이 놓인 줄마다 사각형을 하나씩 화면 위에 얹고 왼쪽에서 오른쪽으로 늘립니다(lineRects → paintSentFill). getClientRects() 는 줄이 아니라 조각을 주므로 — 낱말마다 <span> 이라 한 줄짜리 문장도 쉰 조각이 넘습니다 — 세로로 겹치는 것끼리 묶어 줄로 되돌린 다음, 줄 길이에 비례해 시간을 나눕니다. 글자를 감싸는 방식으로 만들면 문단을 다시 그려야 하고, 그러면 지금 눌러 둔 손가락 밑에서 DOM 이 갈아엎어집니다.

애플의 내장 사전은 막습니다. 그냥 두면 iOS 가 꾹 누르기를 가져가 "복사 / 찾아보기" 를 띄웁니다 — -webkit-touch-callout:none 과 user-select:none(#rtext). 대가는 읽는 화면에서 드래그 선택·복사가 안 되는 것이고, 단어장이 있는 앱에서 본문 복사는 거의 쓰지 않아 이쪽을 골랐습니다.

데스크탑은 같은 코드로 됩니다. 다만 마우스로 0.85초 누르기를 스스로 발견하는 사람은 없으므로, 낱말 창 안에 같은 일을 하는 단추를 하나 둡니다(#p-explain).

웜스타트 — 파란색이 차기 시작하는 순간 함수를 깨웁니다(warmDict). 문장은 보내지 않습니다: 깨우는 요청에는 아무 내용이 없고 한도도 쓰지 않습니다. 취소하면 깨워 둔 것만 남고, 그건 다음 낱말 조회가 씁니다.

한도는 dict_events 의 오늘치 explain 줄을 세서 정합니다(AI_EXPLAIN_DAILY, 기본 5). ai_usage 를 같이 쓰면 문장 설명 다섯 번이 낱말 조회 다섯 번을 잡아먹습니다 — 둘은 성격이 달라 한 통에 담을 수 없습니다. 표를 하나 더 만들지 않아도 되고, 무엇보다 "실제로 답을 받은 횟수"를 세게 됩니다. 받은 답은 s:<문장해시> 로 기기에 남아서, 같은 문장을 다시 물으면 한도를 쓰지 않습니다.

문장은 AI 에게는 갑니다(보내지 않으면 답할 것이 없습니다). 서버에 남는 것은 소금을 섞은 지문과 낱말 수뿐입니다 — 낱말 조회와 완전히 같은 규칙입니다.

기다리는 동안

AI 를 기다리는 자리는 낱말 창과 문장 창 둘인데, 같은 것 하나를 씁니다(.aurora). 기다림의 모양이 자리마다 다르면 "무엇을 기다리는지"가 아니라 "여기가 어디인지"를 먼저 읽게 됩니다.

색은 흰색과 파랑 둘뿐입니다. 옅은 파랑 바탕 위로 흰빛과 짙은 파란빛 덩어리가 서로 다른 자리에서 번지고, 통째로 천천히 밀리고 부풀며 섞입니다. 흐림(blur)이 경계를 지워서 덩어리가 아니라 한 장의 움직이는 빛으로 보입니다. 움직임을 줄여 달라고 설정한 사람에게는 흐르지 않고 숨만 쉽니다.

갓 받은 답과 씨앗은 기다리고, 전에 물어본 답은 곧장 나옵니다. 씨앗은 이 사람이 물어본 적 없는 답이라 화면에서 벌어지는 일은 "지금 물어봤다" 입니다 — 맛보기 글에서만 사전이 이상하게 빨라 보이는 것은 자랑이 아니라 다른 앱처럼 보이는 일이라, AI_MIN_WAIT 만큼 빛을 보여 준 뒤에 놓습니다. 반대로 전에 물어본 답에서 기다림은 거짓말이 됩니다. 곧장 내놓고 머리글도 전에 찾아본 뜻 으로 답니다 — 한도를 쓰지 않았다는 것이 그 자리에서 보이게.

첫 화면에서 받는 것

외부 라이브러리는 Supabase 하나(212KB)뿐입니다. PDF.js 320KB 와 JSZip 98KB 는 파일을 처음 열 때 받습니다(lazy-lib.js) — 기사만 읽는 사람에게는 한 번도 쓰지 않을 짐이었습니다. 단어장 내보내기는 CSV 라 라이브러리가 필요 없습니다. 예전에는 그 버튼 하나 때문에 xlsx 881KB 를 모두가 매번 받았습니다.

index.html 의 우리 파일에는 내용 해시가 ?v= 로 붙습니다(npm run stamp, npm test 가 먼저 돌립니다). GitHub Pages 는 파일마다 캐시를 따로 잡아서, 붙이지 않으면 배포할 때마다 새 index.html 과 옛 sync.js 가 함께 도는 순간이 생깁니다. 해시라서 안 고친 파일의 캐시는 그대로 삽니다.

붙여넣은 글의 모양

parsePastedText는 먼저 무슨 모양인지 알아보고 갈라 보냅니다.

  1. HTML — 앞쪽에 실제 태그가 있고 닫는 태그가 셋 이상이면 parseArticleHtml에 넘깁니다. 기사 URL과 같은 추출기라 규칙을 두 벌 갖고 있지 않습니다. 받아 올 주소가 없는 사진 덩어리는 빼고 다시 조립합니다(문단 번호가 밀리지 않게).
  2. 마크다운 — 구조를 만드는 기호(제목·코드 울타리·표·목록·인용)가 하나는 있어야 하고, 점수도 3점을 넘어야 합니다. 링크 하나 때문에 X 스레드가 카드로 안 펼쳐지는 손해가 더 크기 때문입니다.
  3. 평범한 글 — 예전 그대로. 첫 줄이 제목, 빈 줄이 문단 경계, 빈 줄이 없으면 카드.

마크다운은 # → h1, - → • 항목, > → quote 상자, 표 → note 상자(한 행 한 줄, 칸마다 머리글을 앞에 붙임), 울타리 코드 → code 상자로 옮깁니다. 코드는 한 덩어리로 둡니다 — 줄마다 쪼개면 상자가 스무 개로 늘고 문단 번호가 코드 줄 수만큼 밀립니다. code는 낱말 사전을 걸지 않는 유일한 덩어리입니다.

네이티브 셸 (Capacitor · iOS)

같은 코드를 웹과 앱이 함께 씁니다. 앱 쪽에만 있는 것은 셋뿐입니다.

npm run ios          # www 만들고 → cap sync → Xcode 열기
npm run ios:sync     # 코드만 고쳤을 때
  1. www/ — Capacitor 는 webDir 을 통째로 앱에 복사합니다. 저장소 뿌리를 가리키면 node_modules·ios·docs·sql·server·.git 까지 들어가므로, tools/build-www.mjs 가 브라우저가 실제로 읽는 것만 골라 옮깁니다(1.9MB). 웹 배포는 예전 그대로 빌드 단계가 없습니다 — 이 복사는 앱 번들을 만들 때만 돕니다.
  2. 안전 영역 — viewport-fit=cover 와 env(safe-area-inset-*). 없으면 상단바가 다이내믹 아일랜드 밑으로 들어가고 떠 있는 단추가 홈 인디케이터에 물립니다. 브라우저에서는 이 값이 0 이라 웹 화면은 그대로입니다. contentInset 은 never 입니다. always 였을 때 WKWebView 가 상태 표시줄 높이만큼 띠를 남겨 두어서, 읽는 화면이 시계 아래에서 시작했습니다. never 로 두면 글이 사파리처럼 화면 맨 위까지 흐르고, 시계와 겹치는 자리는 상단바가 자기 padding-top 에 안전 영역을 더해 비켜 줍니다 — 읽어 내려가면 그 상단바가 걷히므로 그때부터는 글이 위까지 다 찹니다. 진행바도 상단바와 함께 걷힙니다. 상단바만 걷고 그 3px 짜리 파란 실을 남겨 두면, 노치 옆 그 자리에 한 줄이 남아 화면이 끝까지 트이지 않습니다 — 사파리에서 주소창이 걷힐 때 아무것도 남지 않는 것과 같은 이유입니다. "얼마나 왔나" 는 눈을 글에서 뗐을 때 궁금한 것이라, 상단바를 되부르는 그 손짓(위로 조금 올리기)에 같이 돌아오면 충분합니다. 자리는 그대로 두고 색만 지웁니다 — 높이를 접으면 글이 3px 튑니다.
  3. 로그인 — 앱 주소는 capacitor://localhost 라 메일 앱이 매직 링크를 열어 주지 못합니다. 그래서 앱 안에서는 emailRedirectTo 를 보내지 않고 6자리 코드로만 들어옵니다(isNativeShell()). 코드 경로는 웹에도 이미 있던 길입니다.

ios/ 는 저장소에 넣고, www/ 와 ios/App/App/public/ 은 생성물이라 넣지 않습니다.

아직 남은 것: PDF.js·JSZip 을 CDN 에서 받아 오므로 앱에서 첫 파일을 열 때 인터넷이 필요합니다. 오프라인이 중요한 앱이라 이건 언젠가 번들에 넣어야 합니다. 앱 아이콘과 스플래시는 Capacitor 기본값이고, 안드로이드는 SDK 가 없어 아직 붙이지 않았습니다.

문서 페이지

docs/ 안의 HTML 은 손으로 고치지 않습니다. tools/build-docs.mjs 가 README.md · DICT.md · ARCHITECTURE.md · ROADMAP.md 를 읽어 다시 굽고, npm test 가 매번 돌립니다. 그래서 문서와 페이지가 어긋날 수 없습니다.

마크다운 파서를 직접 씁니다. 라이브러리를 넣으면 빌드 단계가 생기고, 이 프로젝트는 빌드 단계가 없는 것이 규칙입니다. 우리 문서가 실제로 쓰는 문법만 봅니다 — 제목, 문단, 목록, 표, 코드 블록, 인용, 구분선, 굵게·기울임·인라인 코드·링크. 문서끼리의 .md 링크는 구운 HTML 로, 그 밖의 저장소 파일 링크는 깃허브 주소로 바꿉니다(사이트에서 눌렀을 때 마크다운 원본이 내려오지 않게). 스타일은 파일 안에 박아서 페이지 하나가 그대로 하나의 파일이고, 인쇄용 CSS 가 들어 있어 브라우저 인쇄로 PDF 가 됩니다.

동기화 안전장치

  • 동시에 들어온 자동·수동 동기화 요청은 버리지 않고 현재 작업 뒤에 한 번 더 실행합니다.

  • 서버에서 받은 읽기 위치는 현재 열어 읽는 책의 화면을 갑자기 덮어쓰지 않습니다.
